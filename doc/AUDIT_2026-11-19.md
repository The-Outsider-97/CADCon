# CADCon audit — 2026-11-19

Scope: architecture, conversion, inspection, reporting, comparison, SLAI integration, UI, performance, security, tests and packaging readiness for CADCon (`applications/CADCon`, branch `audit/reconcile-lineages`, based on `a54aec7`). Nothing here has been committed or pushed.

**Verdict: not production-ready.** The Python service, the browser UI and the SLAI integration start, run and pass their tests in a SLAI-shaped layout on Linux. Windows desktop packaging was written the next day (see the 2026-11-20 update below) but has not been built or run; nothing was run on Windows, and the DXF, DWG, IFC and real SLAI-agent paths could not be exercised in this environment. Details are under "Outstanding issues".

## 2. Architecture assessment

- Python backend (`engine.py`, `app.py`, `repair.py`, `utils/`, `slai/bridge/`) runs on SLAI's shared local server (`applications/tools`): loopback only, per-run token, cookie, an `X-SLAI-Cadcon: 1` marker header on mutating requests, responses wrapped as `{ok, data}`.
- TypeScript client in `src/client/`, built by SLAI's shared `build-static.mjs` through `tools/build.mjs`. The build refuses to emit on type errors.
- Five workspaces: Counter, Converter, Analysis & Report, Compare, System. All five render and respond in the browser probe (section 7).
- CADCon owns OBJ and STL I/O. SGEO, SDRW, GLB, SVG, DXF, DWG and IFC are delegated to SLAI adapters, and the size ceilings of those adapters are SLAI kernel limits, not CADCon's.
- **Root cause of the largest defect (D1):** the repository history had two parallel lineages (`28764bf` and `ef82993`, merge base `834877c`). The shipped `repair.py` imported helpers that only one lineage's `engine.py` contained. A three-way merge restored the union. Nothing in CI would have caught it, because CI did not import `repair.py` through the app.
- Zero-byte files remain in the tree: `slai/__init__.py`, `slai/__main__.py`, `slai/api.py`, `slai/app.py`, `slai/bridge/__init__.py`, `src/client/types.ts`, `src/core/api.ts`, `src/core/types.ts`, `tests/__init__.py`. Some are package markers; the rest look like leftovers. I did not delete them because I could not confirm they are unused.

## 6. Performance and measured limits

Icospheres, one operation per process, unindexed STL input, so every triangle carries three vertices. Single run on one sandbox machine; treat as indicative.

| Triangles | Inspect | Analysis | OBJ out | SGEO out | GLB out | Compare (identical) |
|---|---|---|---|---|---|---|
| 1,280 | 0.06 s / 32 MB | 0.05 s | 0.07 s | 0.28 s | 0.2 s | 0.06 s |
| 20,480 | 0.21 s / 67 MB | 0.22 s | 0.65 s / 83 MB | 3.96 s / 95 MB | refused | 0.48 s |
| 81,920 | 1.28 s / 195 MB | 1.19 s | 3.17 s / 256 MB | 18.8 s / 298 MB | refused | 2.5 s |
| 327,680 | 5.2 s / 714 MB | 5.2 s | 14.0 s / 960 MB | refused | refused | 10.5 s |

GLB limit: the SLAI GLB adapter needs `4 × vertices + 6 × triangles ≤ 300,000`. Measured on indexed OBJ: 20,480 triangles (10,242 vertices, 163,848 elements) converts in 1.5 s; 81,920 triangles (40,962 vertices, 655,368 elements) is refused. Unindexed STL reaches the limit about twice as fast, which is why the table shows GLB refused at 20,480 triangles. OBJ and STL are written by CADCon directly. The engine's own `MAX_TRIANGLES` is 600,000; I benchmarked up to 327,680 triangles and did not test larger inputs.

## 8. Security and data-integrity review

What I checked: requests without the session are refused (e2e test); malformed models fail without a traceback (e2e test); an existing destination, including a symlink, is never overwritten or deleted by the failure cleanup (unit test); session directories are owned per process and reaped only when the owner is gone (unit tests). Token, cookie and loopback handling belong to SLAI's shared server, which I used but did not audit. Upload size limits and concurrent-run behaviour were not tested. This is not a penetration test and does not cover third-party libraries. I found no defect beyond D4 and D5.

## 9. SLAI integration

- Startup follows SPADRA / SLAI Writer: shared loader with the `branded` variant, the same events and a visible failure state.
- No SLAI geometry kernel or other app repository was modified. Kernel limits are documented instead (O4).
- The SLAI working tree on the device already had local modifications of its own (for example under `applications/tools`); I did not touch them.
- Integration with SPADRA, SLAI Writer and Documaster beyond shared startup and the shared server was reviewed but not extended.

## 10. Outstanding issues and what a release needs

2. A run with `ezdxf`, an ODA executable and IfcOpenShell (O2), including the four skipped tests.
3. A run with the real SLAI agent stack (O3).
4. Decide the SLAI submodule pointer (O5) and the zero-byte files (O8).
5. Run CI on GitHub (flake8 and the new e2e step).
6. Product decisions: batch conversion, synchronised compare camera, difference heatmaps (O6).
